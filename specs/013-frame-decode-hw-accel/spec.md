# Feature Specification: 帧解码硬件加速

**Feature Branch**: `fix/frame-export-connection-pool`（本功能不单独建分支，沿用用户当前工作分支）

**Created**: 2026-06-23

**Status**: Draft

**Input**: User description: "在工坊（frame-forge）的帧解码路径上新增硬件加速解码支持：跨厂商兼容，Intel（含 Arc 系列如 A380）和 AMD 走 VAAPI（同一套 ffmpeg hwaccel 路径），NVIDIA 走 NVDEC/CUDA hwaccel；硬解初始化失败或解码中途出错时必须优雅降级回退到现有的纯 CPU 软解，不能因为硬解不可用而导致功能整体失败。前端在播放器增强 modal 里新增一个工坊相关设置项：默认勾选"硬件解码"，用户可以取消勾选切回纯软解。背景：当前所有帧提取（缩略图、动图拼接、全景图拼接的逐帧解码）都是纯软解，用户希望提速，但顾虑硬解是否会导致画质下降。已知测试限制：本机开发机只有 NVIDIA RTX 5060 + AMD Raphael 核显，可以验证 NVDEC 和 AMD VAAPI 路径；Intel Arc A380 仅存在于用户的 NAS/生产服务器上，无法在本机验证，只能部署后通过生产日志/截图远程验证。"

## Clarifications

### Session 2026-06-23

- Q: 硬件解码初始化失败/运行时回退到软解时，是否需要专门记录诊断日志（用于后续远程核实 A380 等无法本地验证的硬件是否真正生效）？ → A: 必须记录诊断日志（推荐）
- Q: 检测"当前机器是否存在受支持的硬件解码设备/驱动"（FR-010）这个检测动作应该何时执行？ → A: 服务启动时检测一次并缓存结果（推荐）
- Q: 多硬解设备（如独显+核显）时的默认设备选择规则，应该用哪种判定逻辑？ → A: 提供"性能优先"（默认，独显优先于核显）与"优先使用闲置资源"（动态选择当前负载更低的设备，例如独显正被游戏占用时自动改用核显）两种可选策略，按 PCI 设备分类判定独显/核显，不依赖显示器连接状态
- Q: "优先使用闲置资源"策略下，当某个设备的实时负载数据获取失败（如 Intel 核显的利用率读取比 NVIDIA/AMD 更难获取）时应如何处理？ → A: 回退为静态规则——独显优先（与"性能优先"策略默认行为一致）

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 帧提取整体提速（硬件解码默认开启） (Priority: P1)

用户在工坊里对一个视频做缩略图浏览、动图拼接或全景图拼接时，系统默认使用 GPU 硬件加速解码源视频帧，整体响应速度比纯软件解码更快，用户不需要做任何额外配置即可获得这个提速。

**Why this priority**: 这是用户提出此需求的核心动机——当前纯软解，用户希望提速；默认开启才能让大多数用户无感受益，不必每个人都去手动找设置打开。

**Independent Test**: 在一台已知支持硬件解码的机器（如本机的 NVIDIA/AMD 显卡）上，对同一段视频分别测量"硬件解码开启"和"硬件解码关闭"两种状态下，提取等量帧所需的总耗时，确认开启状态明显更快，且生成的缩略图/动图/全景图与关闭状态下视觉一致。

**Acceptance Scenarios**:

1. **Given** 用户的机器装有受支持的 GPU（NVIDIA / Intel / AMD）且硬件解码功能已开启，**When** 用户在工坊里浏览缩略图、生成动图或拼接全景图，**Then** 系统使用该 GPU 加速解码源视频帧，整体耗时低于纯软解。
2. **Given** 硬件解码已开启，**When** 用户对比硬解和软解生成的同一帧缩略图，**Then** 两者在视觉上应一致（无可感知的画质差异）。
3. **Given** 用户的机器同时存在独立显卡和核显两种受支持的硬件解码设备，且设备选择策略为默认的"性能优先"，**When** 系统执行硬件解码，**Then** 系统选用独立显卡进行解码。
4. **Given** 用户在设置里将设备选择策略切换为"优先使用闲置资源"，且独立显卡当前正被其他任务（如游戏、转码）占用而核显处于空闲，**When** 系统执行硬件解码，**Then** 系统检测到独立显卡负载较高，自动选用当前更空闲的核显进行解码。
5. **Given** 设备选择策略为"优先使用闲置资源"，且独立显卡当前实际处于空闲状态，**When** 系统执行硬件解码，**Then** 系统应能选用当前更空闲的独立显卡，而不是无条件固定使用核显。

---

### User Story 2 - 用户可手动关闭硬件解码退回纯软解 (Priority: P2)

用户怀疑硬件解码在自己的设备上有问题（画质、稳定性或兼容性疑虑），可以在播放器增强 modal 的工坊相关设置里手动取消"硬件解码"勾选，系统改用现有的纯 CPU 软件解码路径，且这个设置会被记住。

**Why this priority**: 给用户一个可控的退路，降低硬解功能上线后的风险——即使某些环境下硬解表现不佳，用户也不会被卡住，可以立即自助切回已知可靠的软解路径。

**Independent Test**: 在设置里取消"硬件解码"勾选后，重新触发一次帧提取操作，确认系统不再调用任何 GPU 硬件解码路径，行为与硬件加速功能上线前完全一致；关闭/重新打开 modal 或重启服务后，该设置仍保持用户上次选择的状态。

**Acceptance Scenarios**:

1. **Given** 用户在播放器增强 modal 的工坊设置里取消勾选"硬件解码"，**When** 用户再次进行缩略图浏览/动图拼接/全景图拼接，**Then** 系统全程使用纯 CPU 软件解码，不尝试调用任何 GPU 硬件解码路径。
2. **Given** 用户曾经手动关闭过硬件解码，**When** 用户关闭并重新打开播放器增强 modal，或服务重启后再次进入工坊，**Then** "硬件解码"的勾选状态仍保持用户上次设置的关闭状态。
3. **Given** 用户的机器上检测不到任何受支持的硬件解码设备/驱动，**When** 用户打开播放器增强 modal 的工坊设置，**Then** "硬件解码"开关显示为禁用（不可勾选）状态，并附带提示说明当前环境不支持硬件解码。

---

### User Story 3 - 硬件解码不可用或失败时自动优雅降级 (Priority: P1)

当用户的硬件不支持硬件解码、驱动缺失、或硬件解码在某次具体操作中途失败时，系统自动退回纯软件解码继续完成当前操作，不会因为硬件解码的问题导致整个帧提取功能失败或用户操作卡死/报错中断。

**Why this priority**: 这是硬件加速功能能安全上线的前提——用户明确要求"不能因为硬解不可用而导致功能整体失败"，这是跨厂商兼容、覆盖各种用户实际硬件环境（尤其是用户自己那台 Intel Arc A380，团队无法在开发环境直接验证）时风险最高的一环，必须作为与"提速"同等优先级的核心需求。

**Independent Test**: 在一台不支持硬件解码（或故意让硬件解码初始化失败）的环境下，确认帧提取操作仍能完整成功，输出结果与纯软解路径一致；在硬件解码已开始但中途遇到解码错误的场景下，确认当前这一帧及后续帧能够回退到软解完成，而不是让整个任务失败或挂起。

**Acceptance Scenarios**:

1. **Given** 用户的硬件不支持硬件加速解码（驱动缺失或硬件本身不支持），**When** 系统尝试初始化硬件解码失败，**Then** 系统自动改用现有的纯软件解码完成本次操作，用户不会看到任何错误提示或功能中断。
2. **Given** 硬件解码已经开始处理某个视频，**When** 某一帧的硬件解码过程中途出错，**Then** 系统对该帧（以及后续帧）自动回退到软件解码，最终任务仍能正常完成。

---

### Edge Cases

- 用户的设备同时有多块 GPU（如独显+核显）时，系统如何选择使用哪一块？（提供"性能优先"与"优先使用闲置资源"两种可选策略，见 FR-012；按 PCI 设备分类区分独显/核显，不依赖显示器连接状态——后者在无显示器的服务器环境下没有意义）
- "优先使用闲置资源"策略下，用户的独立显卡正被其他任务（如游戏、视频转码）占用时会发生什么？（系统需要动态检测各设备的实时负载，自动改用当前更空闲的设备（通常是核显），而不是静态地"永远用核显"——如果反过来独显空闲、核显忙，也应选择独显）
- 当某个硬件解码设备的实时负载数据无法获取（如部分 Intel 驱动不暴露利用率指标）时，"优先使用闲置资源"策略如何降级？（回退为与"性能优先"相同的静态规则：独显优先）
- 机器上只有一个（或零个）受支持的硬件解码设备时，"性能优先/优先使用闲置资源"这个策略选择项是否展示？（不展示——只有检测到多个受支持设备时才显示该选择项，避免在不产生任何行为差异的情况下让用户面对一个无意义的选项）
- 源视频是 10-bit / HDR 内容，而硬件解码器只支持 8-bit 时会发生什么？（视为"硬件解码不支持该内容"的一种失败场景，必须按 User Story 3 的优雅降级规则退回软解，不允许静默截断位深导致画质劣化）
- 同一个视频里部分帧硬解成功、部分帧硬解失败（比如解码器在特定帧类型上出问题）混合出现时，最终生成的动图/全景图是否会因为软硬解输出存在极细微差异而出现可见的拼接不一致？（需要在验收时人工检查，作为已知风险记录，而非强制要求与某个量化阈值比较）
- 用户关闭硬件解码开关的时机，恰好是某个帧提取任务正在进行中，这个正在进行的任务是否需要立即切换，还是等当前任务结束后才生效？（约定：当前进行中的任务沿用任务开始时读取到的设置，不动态打断；下一次新发起的操作生效新设置）
- 用户机器上完全没有受支持的硬件解码设备/驱动时，开关应直接禁用并提示，而不是允许用户勾选一个实际不会生效的选项（避免用户误以为硬件解码已启用却毫无效果，分不清是"没生效"还是"没提速"）。
- 某些硬件解码设备对某些编码格式实际上比软解更慢（已实测：AMD Raphael 核显 VAAPI 解 AV1 10-bit 比软解慢 ~2 倍，见 quickstart.md"已知限制"）时怎么办？（不在"优先使用闲置资源"策略里动态判断软解/硬解哪个更快——按 codec/分辨率/设备型号实时判断需要维护实测基准表，超出本 spec 范围；用户可直接关闭硬件解码父开关退回纯软解，这正是该开关存在的用途之一）

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 在源视频解码阶段（缩略图提取、动图拼接、全景图拼接所涉及的逐帧解码，覆盖目前所有使用纯软件解码的帧提取路径）支持使用 GPU 硬件加速解码。
- **FR-002**: 系统 MUST 支持至少以下三类 GPU 厂商的硬件加速解码：Intel（含独立显卡型号，如 Arc 系列）、AMD、NVIDIA。
- **FR-003**: 系统 MUST 在硬件解码初始化失败（如所需驱动/运行时缺失、设备不支持该编码格式）时自动退回现有的纯软件解码路径，且该次帧提取操作仍需正常完成。
- **FR-004**: 系统 MUST 在硬件解码已开始但执行过程中失败（单帧或部分帧解码出错）时，对受影响的帧自动退回软件解码，不得导致整个帧提取/拼接任务失败或挂起。
- **FR-005**: 系统 MUST 提供一个用户可见、可操作的开关，用于启用或禁用硬件解码；该开关位于播放器增强 modal 的工坊相关设置区域。
- **FR-006**: 该开关 MUST 默认处于"启用硬件解码"状态。
- **FR-007**: 用户对该开关的选择 MUST 被持久化保存，在用户重新打开播放器增强 modal、或服务重启后依然保持用户上次的选择。
- **FR-008**: 当用户关闭该开关时，系统 MUST 完全不尝试调用任何硬件解码路径，行为等同于硬件加速功能未上线之前的纯软件解码。
- **FR-009**: 硬件解码产出的图像数据，在编码为最终的缩略图/动图/全景图输出格式之前，MUST 与现有软件解码路径输出在视觉上保持一致（不存在可感知的画质劣化）。
- **FR-010**: 系统 MUST 检测当前机器上是否存在受支持的硬件解码设备/驱动；该检测 MUST 在服务启动时执行一次并缓存结果（不在每次打开 modal 时重新检测，重新检测需要重启服务）；当检测结果为"不支持"时，播放器增强 modal 里的硬件解码开关 MUST 显示为禁用（不可勾选）状态，并向用户展示提示信息说明当前环境不支持硬件解码。
- **FR-011**: 系统 MUST 将硬件解码的初始化结果（成功/失败及原因）以及运行时回退到软件解码的事件记录到诊断日志中，用于在无法本地验证的硬件环境（如生产/NAS 服务器上的设备）上事后核实硬件解码是否真正生效；该日志面向运维/开发排查，不在终端用户界面展示。
- **FR-012**: 当机器上同时存在多个受支持的硬件解码设备时，系统 MUST 提供"性能优先"与"优先使用闲置资源"两种可选的设备选择策略；该策略选择 MUST 与硬件解码开关一样持久化保存，且判定独显/核显 MUST 基于 PCI 设备分类，不依赖显示器连接状态。该策略选择项 MUST 仅在检测到多个受支持的硬件解码设备时才在播放器增强 modal 中显示；只有一个（或零个）受支持设备的机器上不展示该选择项。
  - **性能优先**（默认）：MUST 优先选用独立显卡，核显仅在没有独立显卡时使用，不考虑设备当前实时负载。
  - **优先使用闲置资源**：MUST 在执行硬件解码前动态检测各候选设备当前的实时负载，选择负载较低（更空闲）的设备——例如独立显卡正被游戏或转码占用时自动改用核显，反之独立显卡空闲时也可继续选用独立显卡；当某个设备的实时负载数据无法获取时，MUST 针对该次选择降级为"性能优先"的静态规则（独显优先）。

### Key Entities

- **硬件解码开关设置**：用户对"是否启用硬件解码"的选择，属于插件级别的持久化配置（而非单次会话的临时状态），影响该插件实例上后续所有帧提取操作。
- **硬件解码设备选择策略**：当存在多个硬件解码设备时，用户对"性能优先"（静态独显优先，忽略实时负载）或"优先使用闲置资源"（动态按实时负载选最空闲设备，负载数据不可用时降级为静态独显优先）的选择，同属插件级别的持久化配置，独立于硬件解码开关本身。该选择项仅在检测到多个受支持设备时才在 UI 中展示；只有一个设备时该设置仍会被持久化保存（保留用户曾经的选择，以备后续插拔新设备后立即生效），但 UI 不展示，也不产生可观察的行为差异。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**：在支持硬件解码的设备上，处理同一段视频、提取同等数量帧时，启用硬件解码后的总耗时**不劣于**纯软件解码，且应有可观测的净提速（不要求固定百分比）。*（已修正，原定 ≥30%：2026-06-23 实测发现，缩略图预取这条路径的耗时主体是逐帧 WebP 编码（约 180-200ms/帧），解码本身（硬解或软解）仅占 1-2ms/帧——硬解相对软解能省下的时间，对编码这座大头而言占比很小，实测净提速约 7%（186ms/帧 vs 198ms/帧，1080p10 AV1，RTX 5060 NVDEC）。硬解在此workload下唯一的净收益是把 CPU 从软解的多线程切片解码中释放出来；若需要更大幅度提速，需要优化 WebP 编码本身（如调整编码参数、并行化 lossy/lossless 双输出），那是独立于本功能范围的课题。）*
- **SC-002**: 在硬件解码不支持或主动关闭的设备/配置下，帧提取功能的成功率与现有纯软件解码版本保持一致（100% 功能可用，零因硬件解码相关原因导致的失败）。
- **SC-003**: 人工随机抽样对比硬解与软解输出的同一帧缩略图/动图/全景图，在视觉上无法分辨差异。
- **SC-004**: 用户对硬件解码开关的设置变更后，下一次帧提取操作 100% 按照用户最新选择的模式（硬解或软解）执行。
- **SC-005**: 在没有受支持硬件解码设备/驱动的机器上，播放器增强 modal 里的硬件解码开关 100% 处于禁用状态并显示对应提示，不存在用户可以勾选一个无效选项的情况。
- **SC-006**: 在同时具备独立显卡和核显的机器上，"性能优先"策略下 100% 选用独立显卡执行硬件解码（不受设备当前负载影响）；"优先使用闲置资源"策略下，当独立显卡被其他任务占用时 100% 自动改用当前更空闲的核显执行硬件解码，独立显卡空闲时仍可继续选用独立显卡。

## Assumptions

- 硬件解码开关是插件级别的全局设置（影响该 Jellyfin 插件实例上的所有用户/所有视频），不是每个视频单独配置，也不是按登录用户区分的个人偏好——这与工坊功能现有的其他全局配置项（如设备选择、模型版本）保持一致的管理方式。
- 多设备时的默认选择策略按 FR-012 执行（"性能优先"默认独显优先于核显），与 Real-ESRGAN 提升画质功能现有的设备枚举机制共享同一套设备发现/分类逻辑，但硬件解码引入了独立于 Real-ESRGAN 的"性能优先/优先使用闲置资源"二选一设置项（而非完全复用 Real-ESRGAN 现有的"按枚举顺序选第一个 GPU"默认逻辑，因为该现有逻辑未真正区分独显/核显）。
- 性能验收（SC-001）以"硬解不慢于软解、且有可观测净提速"为基准，不保证对所有编码格式/分辨率/输出尺寸组合都有同等比例的提速——见 SC-001 已修正说明，提速幅度受限于下游 WebP 编码这一更大的固定成本。
- Intel Arc A380 这类只存在于用户生产/NAS 环境、团队开发环境无法直接验证的硬件，其验收依赖部署后由用户在生产环境实测确认（参考此前 OpenVINO GPU EP 在同一硬件上的验证方式：日志 + 实际效果反馈），不要求在功能合入前于本地完成该型号硬件的验证。
- 10-bit/HDR 内容的位深兼容性问题，按 Edge Cases 中约定的规则处理（视为硬件解码不支持，触发优雅降级），不要求本功能范围内额外开发"检测到位深不支持时给用户提示"的 UI。
